# Pinned v1.1.0 → v1.2.0 upgrade and rollback qualification

**Status: compatibility investigation, not release approval.** The actual published v1.1.0 source and nominated v1.2.0 candidate are tested in separate read-only checkouts. All installation and restoration happen in disposable Windows directories; there are no external bootstraps, live databases, IDE installations, or production mutations.

The acceptance script verifies both checkout HEADs and their `VERSION` files before creating any fixture. Testing `develop` in place of the pinned candidate is not valid release evidence.

## What the Windows job exercises

1. Install v1.1.0 into a temporary MongoDB-signaled repository. Add a repository-owned customized Copilot skill and verification profile; take a complete byte-for-byte snapshot before upgrade.
2. Reinstall from v1.2.0 with default `-ConflictMode skip`. Verify every preexisting file is preserved (except the installer-owned manifest), all three new data skills are copied from the candidate, and the manifest reports 1.2.0.
3. **Detect the partial-upgrade hazard:** `skip` retains the old Doctor even though the manifest is now 1.2.0. The skill catalog happens to be byte-identical across these two pinned commits; it is not the source of the version mismatch. This is **not** treated as a completed runtime migration.
4. On a separate snapshot copy, use explicitly requested `-ConflictMode overwrite`. Verify candidate runtime/catalog and Doctor readiness, and demonstrate that overwrite also replaces a repository-owned customization. This is an **unsafe default** for customer repositories.
5. Restore both variants from the pre-upgrade snapshot. Compare every file path and SHA-256 with the original, verify manifest 1.1.0, and confirm v1.2-only skills are absent. This validates **snapshot restoration**, not an unsupported in-place downgrade.
6. Emit a redacted JSON receipt containing the two exact source SHAs, assertion outcomes and the **BLOCKED** release gate disposition. The workflow uploads it as an expiring CI artifact.

The tests do not claim that a routine `skip` install upgrades all runtime code, that `overwrite` protects customized files, or that a real developer's IDE/environment was tested. The job may pass while **Q-09 remains BLOCKED**, because detecting and proving a compatibility limitation is useful qualification evidence.

pwsh ./tests/release-1-2-upgrade-rollback-smoke.ps1 -BaselineSourcePath "C:\temp\harness-v1-1" -CandidateSourcePath "C:\temp\harness-v1-2" -ReceiptPath "C:\temp\upgrade-receipt.json"

The disposable target is created inside the system temporary directory and removed after execution. The source checkouts are never modified. Do not point the installer at a real user repository for this qualification test.

## Provisional managed-upgrade implementation (develop, not the nominated candidate)

The next implementation introduces an explicit `-ConflictMode managed-upgrade` on `develop`. It is evaluated independently against an immutable published v1.1.0 checkout by `tests/managed-upgrade-smoke.ps1`. **This is PR integration evidence, not proof that the pinned `main` candidate is fixed.**

- **Preflight:** requires an existing 1.1.0 manifest, compares all installed managed paths to exact v1.1.0 Git-blob fingerprints captured from commit `1996bba`, and aborts before mutation if a managed skill, script, or instruction was customized. New 1.2.0-only paths must be absent. A pristine file already matching 1.2.0 is accepted.
- **Isolation:** `managed-upgrade` requires `-SkipSpecKit -SkipCodeGraph -SkipVerificationProfile` so external bootstraps and user verification profiles are outside the transactional file set. The baseline map is a pristine-file detector, **not** a signature or supply-chain authenticity proof.
- **Backup:** original managed files and the v1.1.0 manifest are saved under `.copilot-harness/backups/<timestamp>-<id>/files/`. A receipt records original SHA-256 hashes and newly introduced paths.
- **Rollback:** a failed install restores the backed-up managed paths automatically. An explicit restore command also restores the exact original files and removes only paths the managed upgrade introduced. The backup directory remains as audit evidence; do not use the restore command after independently editing upgraded managed files.
- **Manifest:** a clean managed upgrade reports `harnessVersion: 1.2.0`, `upgrade.status: COMPLETE` and `upgrade.backupPath`. Default `skip` still preserves user files, but if any differing managed file was skipped, it reports `upgrade.status: PARTIAL` and retains the previous effective `harnessVersion` rather than claiming a complete runtime upgrade.
- **Conflict resolution:** back up and review customized files manually, decide whether to rebase customizations on current templates, then retry only after the preflight is clean. No silent overwrite and no automatic merge of custom content is attempted.

Example on a **disposable or separately backed-up** v1.1.0 repository, using the *fix branch installer*:

```powershell
pwsh ./installer/install.ps1 -TargetPath "C:\\temp\\repo" -ConflictMode managed-upgrade -SkipSpecKit -SkipCodeGraph -SkipVerificationProfile -SkipDoctor
# Read the backupPath returned in C:\\temp\\repo\\.copilot-harness.json
pwsh ./installer/restore-managed-upgrade.ps1 -TargetPath "C:\\temp\\repo" -BackupPath "C:\\temp\\repo\\.copilot-harness\\backups\\<id>"
```

This workflow does not cover arbitrary older harness versions, custom edits to managed files, third-party setup, or post-upgrade edits. Those situations remain explicit review and manual-migration paths.
