# Pinned v1.1.0 → v1.2.0 upgrade and rollback qualification

**Status: compatibility investigation, not release approval.** The actual published v1.1.0 source and nominated v1.2.0 candidate are tested in separate read-only checkouts. All installation and restoration happen in disposable Windows directories; there are no external bootstraps, live databases, IDE installations, or production mutations.

The acceptance script verifies both checkout HEADs and their `VERSION` files before creating any fixture. Testing `develop` in place of the pinned candidate is not valid release evidence.

## What the Windows job exercises

1. Install v1.1.0 into a temporary MongoDB-signaled repository. Add a repository-owned customized Copilot skill and verification profile; take a complete byte-for-byte snapshot before upgrade.
2. Reinstall from v1.2.0 with default `-ConflictMode skip`. Verify every preexisting file is preserved (except the installer-owned manifest), all three new data skills are copied from the candidate, and the manifest reports 1.2.0.
3. **Detect the partial-upgrade hazard:** `skip` retains the old Doctor and skill catalog even though the manifest is now 1.2.0. This is deliberately documented and is **not** treated as a completed runtime migration.
4. On a separate snapshot copy, use explicitly requested `-ConflictMode overwrite`. Verify candidate runtime/catalog and Doctor readiness, and demonstrate that overwrite also replaces a repository-owned customization. This is an **unsafe default** for customer repositories.
5. Restore both variants from the pre-upgrade snapshot. Compare every file path and SHA-256 with the original, verify manifest 1.1.0, and confirm v1.2-only skills are absent. This validates **snapshot restoration**, not an unsupported in-place downgrade.
6. Emit a redacted JSON receipt containing the two exact source SHAs, assertion outcomes and the **BLOCKED** release gate disposition. The workflow uploads it as an expiring CI artifact.

The tests do not claim that a routine `skip` install upgrades all runtime code, that `overwrite` protects customized files, or that a real developer's IDE/environment was tested. The job may pass while **Q-09 remains BLOCKED**, because detecting and proving a compatibility limitation is useful qualification evidence.

## Reproduction (Windows PowerShell)

Check out the two commits above into separate read-only source directories, then run from this repository:

```powershell
pwsh ./tests/release-1-2-upgrade-rollback-smoke.ps1 -BaselineSourcePath "C:\temp\harness-v1-1" -CandidateSourcePath "C:\temp\harness-v1-2" -ReceiptPath "C:\temp\upgrade-receipt.json"
```

The disposable target is created inside the system temporary directory and removed after execution. The source checkouts are never modified. Do not point the installer at a real user repository for this qualification test.

Re-run the final release-head CI after any candidate changes.

**No v1.2.0 tag or GitHub Release may be created from this evidence alone.**
