# v1.1.0 Release Qualification Plan

**Status:** CANDIDATE — not released. **Baseline:** v1.0.0 (`main`). **Candidate source:** `develop`. **Proposed release branch:** `release/1.1.0`.

## Scope

Release the post-v1.0 native skill and evaluation improvements, including interaction skills, native ASP.NET Core and Angular reviews, installer/upgrade acceptance, skill selection regression tests, and the IDE adoption review kit. These are **tooling and evaluation capabilities**, not proof that Copilot IDE integration has passed in a real developer environment.

## Required gates

| Gate | Evidence | State |
| --- | --- | --- |
| Compare main/develop, confirm intended changes only | Compare link and reviewed file list | NOT RUN |
| Validate PowerShell AST and JSON schemas | Harness Smoke run and commit SHA | NOT RUN |
| Fresh installation and upgrade preservation | `tests/install-upgrade-smoke.ps1` and `tests/native-skill-adoption-smoke.ps1` | NOT RUN |
| Native skill selector regression | Harness eval suite and native skill smoke | NOT RUN |
| IDE adoption review in actual VS Code and Visual Studio | Redacted review file, exact IDE/Copilot versions | BLOCKED |
| Validate release documentation, links, license/provenance and secret scan | Reviewer checklist | NOT RUN |
| Release-head CI | Workflow run URL and green conclusion | NOT RUN |
| Upgrade from v1.0.0 in disposable representative repositories | Install/Doctor reports and diffs | NOT RUN |
| Rollback and compatibility review | Restore procedure and manifest comparison | NOT RUN |

## Promotion rules

1. No release until the required automated gates pass and evidence is recorded.
2. **BLOCKED**, **NOT RUN** and **SKIPPED** are not PASS. IDE adoption can be explicitly deferred only if the release notes state that IDE behavior is unverified and a reviewer accepts that limitation.
3. Use `release/1.1.0` from `develop` after scope freeze. Update `VERSION` and `CHANGELOG.md` **on that release branch**, not in this planning PR.
4. Merge release branch to `main` only after release-head CI and review; tag `v1.1.0` on the final release commit; synchronize `main` back to `develop` immediately after promotion.
5. Do not force-update `develop` or rewrite release history.

## Rollback

Keep `v1.0.0` available as the known baseline. If v1.1.0 qualification fails, do not promote; fix on release branch or postpone. If an installed repo has issues, restore backed-up repository-owned files and reinstall the pinned v1.0.0 version with default `skip` conflict mode; do not claim a rollback has been tested without executing it.

## Versioning rationale

The candidate is **minor 1.1.0** because it adds backward-compatible native skill and evaluation functionality. If qualification reveals incompatible installer or catalog changes, stop and reassess semantic versioning before promotion.
